# sas-specify-function

LLM의 행동을 정의하는 행동 지침서를 쓴다. 산출물만으로 LLM이 그 기능을 수행할 수 있어야
한다. 1차 독자는 지침서를 실행하는 LLM이고, 사람은 유지보수할 때 읽는다. 그래서 배경
설명보다 기준이 앞선다.

## 입력

- 요청 본문. 호출 인자에서 읽는다.
- 참조 자료. 기존 코드·문서·선행 지침서.
- 저장 경로. `--path <경로>`로 받고, 없으면 질의한다.

## 절차

1. 수집. 요청과 참조 자료를 모으고 대상 유형의 작성법을 확인한다. 지침서가 기댈
   스킬·에이전트·도구·경로가 실제로 있는지 확인한다.
2. 질의. 모호·상충·누락 항목을 한 번에 모아 사용자에게 묻는다. 다른 스킬·에이전트 호출이나
   프로젝트 규칙을 넣는 것이 좋겠다고 판단되면 넣지 말고 여기서 제안한다. 답을 받기 전에는
   초안을 쓰지 않는다. 남는 질의가 있으면 1로 돌아간다.
3. 작성. `sas-lean-writing` 스킬을 호출해 글쓰기 기준을 적용하고, 아래 작성 기준대로 쓴
   뒤 저장한다. 기존 파일이 있으면 덮어쓸지 확인한다.
4. 보고. 저장 경로와 변경·특이 사항을 알린다. 본문은 다시 출력하지 않는다.

## 작성 기준

- **유효한 핵심만 서술한다.** 대상 유형의 작성법을 확인한 뒤, 결과를 좌우하는 기준·제약·
  절차 등 유효한 핵심만 적어 간결함을 유지한다. 유효하다는 것은 실제로 존재하고
  동작한다는 뜻이다. 없는 스킬을 부르거나 실행 주체가 쓸 수 없는 도구를 절차에 넣지
  않는다. 무엇이 핵심인지는 기능마다 다르므로 작성자가 판단한다.
- **요청한 것만 넣는다.** 지침서에 담는 내용의 출처는 사용자의 요청과 질의에 대한 답,
  사용자가 가리킨 참조 자료, 대상 유형의 작성법 셋뿐이다. 프로젝트 지침(CLAUDE.md·AGENTS.md
  등)의 규칙과 설치된 스킬·에이전트 목록은 요청을 이해하고 존재를 확인하는 데만 쓴다.
  거기서 온 규칙과 호출, 감사·리뷰가 요구하는 다른 스킬·에이전트 언급은 사용자가
  요청했거나 질의에 그렇게 답한 경우에만 적는다. 도구 목록에 Skill·Agent를 두는 것은 실행
  LLM이 스스로 고르게 하는 것이라 호출 지정이 아니고, 본문에서 특정 스킬·에이전트를
  이름으로 부르게 하는 것이 지정이다.
- **공통 규칙은 넣지 않는다.** 임시 파일 처리, 영역 분담, 외부 조회 시 비공개 정보 보호,
  도구 선호처럼 어느 스킬·에이전트에나 해당하는 규칙은 프로젝트 지침의 몫이다. 필요하다고
  보면 지침서에 넣지 않고 프로젝트 지침 수정을 따로 제안한다.
- **해석이 하나로 수렴하게 쓴다.** 상충하는 지시와 모호한 표현을 없앤다.
- **요청 범위만 수정한다.** 필요하면 범위 밖의 확장 수정을 제안하되, 실행은 사용자 확인
  뒤에 한다.
- **자기완결의 단위는 산출물 전체다.** 정의 파일과 그 파일이 명시적으로 부르는 같은 산출물의
  파일을 합친 것이다. 스킬은 SKILL.md와 그 폴더의 references·scripts 등이고, 훅은 등록
  설정과 그것이 부르는 스크립트다. 에이전트와 커맨드는 보통 파일 하나다. 산출물 안의 파일을
  가리키는 것과 사용자가 지정한 다른 스킬·에이전트를 호출하는 것은 존재하는 것에 한해
  허용한다. 그 밖의 저장소 문서나 특정 환경을 근거로 끌어오지 않는다.
- **글쓰기는 `sas-lean-writing`을 따른다.** 표기, 군더더기, 이력, 구조, 흐름은 그 기준대로
  한다.
