# PRP 플로우를 건축에 빗대어 읽기

이 문서는 사람이 PRP 플로우를 이해하기 위한 설명이다. 스킬 실행에는 쓰이지 않으며, 동작의 기준은
각 스킬의 `SKILL.md` 다. 여기서는 기능 하나를 만드는 과정을 건물 한 채를 짓는 과정에 빗대어
설명한다.

## 한눈에 보는 흐름

```text
발주자(사용자)의 요청
   ↓
[sas-prp-prd]   계약서 작성: 요구 정리와 컨펌, 사전 조사, 설계 기준 확정, PRD와 부속 서류
   ↓
[sas-prp-plan]  공정별 상세 계획: 다음 공정을 골라 실행 계획을 씀        ┐
   ↓                                                                    │ 공정마다 반복
[sas-prp-task]  현장 시공: 검사 기준 → 시공 → 검수 → 마감 정리 → 공정 완료 보고 ┘
   ↓
[sas-prp-pr]    준공 검사와 인수 요청: 전체 감사, 결함 수정, PR
   ↓
발주자의 인수: PR 검토와 머지
```

`sas-prp-flow` 는 이 그림 밖에 있다. 공정표를 읽어 다음 공정을 대신 불러 주는 자동화 편의 기능일
뿐이며, 건축 비유로는 대응하는 사람이 없다.

## 등장인물

| 건축                       | PRP                               | 하는 일                                                                         |
| -------------------------- | --------------------------------- | ------------------------------------------------------------------------------- |
| 발주자                     | 사용자                            | 무엇을 원하는지 말하고, 계약서를 컨펌하고, 마지막에 인수한다                    |
| 시공사                     | 메인 에이전트(Claude)             | 계약서를 정리하고 공정을 관리하며, 커밋은 시공사만 한다                         |
| 사전 조사팀                | `sas-higency-persona` 에이전트    | 요청의 전제가 사실인지 확인하고, 더 나은 공법·자재가 있는지 찾는다              |
| 설계 기준 담당             | `sas-governance-guide` 에이전트   | 이 현장의 규격과 검사 도구를 정해 선택지로 내놓는다                             |
| 완전성 검수팀              | `sas-stickler-persona` 에이전트   | 합의·조사 내용이 계약서·계획에 빠짐없이 담겼는지 항목별로 확인한다              |
| 공정별 전문가              | `/prp-plan`                       | 자기 공정의 상세 실행 계획을 쓴다(현장 가이드 조사는 사전 조사팀이 다시 맡는다) |
| 검사 기준을 먼저 세우는 팀 | `sas-tdd-guide` 에이전트          | 무엇이 되어야 합격인지 검사 기준(RED 테스트)을 먼저 만든다                      |
| 시공팀                     | Codex                             | 검사 기준을 통과하도록 만든다(GREEN)                                            |
| 검수자                     | `sas-audit-code` 스킬             | 시공 뒤와 공정 끝에 결함을 찾는다                                               |
| 마감 정리 반장             | `sas-refactoring-master` 에이전트 | 공정이 끝난 뒤 구조와 이름을 정리해 완성도를 올린다                             |
| 서류 정리                  | `sas-file-cleanup` 스킬           | 준공 뒤 계약 서류를 보관하고 남길 결정을 메모리에 옮긴다                        |

## 1단계, 계약서를 쓴다 (`sas-prp-prd`)

발주자의 요청을 받아 시공사가 계약서를 만드는 단계다. 계약서인 PRD 에는 왜 짓는지, 무엇을 짓고
무엇은 짓지 않는지, 어떤 제약과 합의가 있는지, 어떤 방향으로 갈지, 그리고 공정을 어떻게 나눌지가
들어간다.

1. **요구 정리와 컨펌.** 발주자가 말한 것과 대화에서 합의한 것을 목표, 범위, 요구 목록, 제약,
   미결 사항으로 정리해 발주자에게 확인받는다. 이 컨펌 내용이 이후 모든 단계의 출발점이다.
2. **시장·현장 조사.** 비슷한 선례가 있는지, 최근 동향이 바뀐 게 있는지 가볍게 훑는다.
3. **기술 타당성 조사와 설계 기준 확정.** 사전 조사팀(일잘러)이 요청의 전제가 사실인지
   확인하고, 요청한 방식보다 표준·관행에 비춰 더 나은 대안이 있는지 종류를 가리지 않고 찾는다.
   패키지와 알고리즘만이 아니라 린트, CI, 프로세스도 대안이 된다. 예를 들어 "하드코딩 스타일
   토큰을 막고 싶다"는 요청에는 테스트를 짜기 전에 린트 도입이 대안이 된다. 이때 설계 기준
   담당(거버넌스 가이드)을 반드시 함께 불러, 현장의 기존 규격, 업계 표준, 앞으로의 확장성 세
   축으로 컨벤션을 판별하고 규칙마다 그것을 지키게 할 검사 도구(린트·정적 분석·테스트)까지
   붙여 선택지로 내놓게 한다. 결정은 발주자가 한다. 이미 규격 안에 있는 요청이면 판별할 것이
   없다고 답한다. 조사 근거는 같은 폴더의 `research.md` 에 남는다.
4. **계약서와 부속 서류.** PRD 를 쓴다. 시장·현장 조사 결과는 PRD 안에, 기술 조사 결과는
   `research.md` 요약으로 들어간다. PRD 에 담기지 않은 합의·데이터 모델은 같은 폴더에
   `contract.md`, `data-model.md` 같은 부속 서류로 남긴다. 완전성 검수팀(원칙러)이 컨펌한
   내용이 어디에든 빠짐없이 적혔는지 항목별로 확인한 뒤, 브랜치를 만들고 커밋한다.

공정 분해는 이 단계에서 끝난다. PRD 의 Implementation Phases 표가 공정 목록이고, 표의
Parallel·Depends 열이 병렬 가능 여부와 선후 관계다.

## 2단계, 공정별 상세 계획을 쓴다 (`sas-prp-plan`)

계약서의 공정 목록에서 선후 관계가 풀린 다음 공정을 골라, 그 공정 하나의 실행 계획 `plan.md` 를
쓴다. 쓰는 과정에서 사전 조사팀(일잘러)이 설계 기준 담당도 함께 불러 이 공정의 구현 현장
가이드(예: 특정 반환 형식·패턴의 채택 여부 같은 실무 규칙)를 조사해 같은 폴더의 `research.md`
로 남기고, 완전성 검수팀(원칙러)이 계약서·부속 서류·조사 결과와 어긋나지 않는지 확인한 뒤
커밋한다. 이때 그 공정의 상태가 `pending` 에서 `in-progress` 로 바뀐다. 병렬로 갈 수 있는 공정이
여럿이면 어느 것부터 할지는 발주자가 고른다.

## 3단계, 현장에서 짓는다 (`sas-prp-task`)

한 공정을 실제로 만드는 단계다. 순서가 중요하다.

| 순서 | 현장 비유             | 실제                                                                                           |
| ---- | --------------------- | ---------------------------------------------------------------------------------------------- |
| 1    | 검사 기준을 먼저 세움 | `sas-tdd-guide` 가 실패하는 RED 테스트를 쓰고, 시공팀에 넘길 인계 사항을 남긴다                |
| 2    | 시공                  | Codex 가 그 테스트를 통과시키는 최소 구현을 만든다(GREEN)                                      |
| 3    | 검수                  | `sas-audit-code --mini` 가 아직 커밋하지 않은 GREEN 변경을 검사하고, 결함은 시공팀이 고친다    |
| 4    | 커밋                  | RED 와 GREEN 을 각각 커밋한다                                                                  |
| 5    | 마감 정리             | 공정의 GREEN 이 모두 끝나면 `sas-refactoring-master` 가 구조와 이름을 정리한다. 한 번만 한다   |
| 6    | 공정 검사             | `sas-audit-code --mini` 가 이 공정에서 생긴 모든 변경을 검사한다. 중간에 낀 잡다한 수정도 포함 |
| 7    | 공정 완료 보고        | 계획하며 바뀐 것 중 중요한 결정을 계약서에 반영하고 공정 상태를 `complete` 로 바꾼다           |

검사 기준을 세우는 팀과 시공팀을 나누는 이유는, 문제를 낸 쪽이 스스로 풀면 통과하기 쉬운 쪽으로
느슨해지기 때문이다. 마감 정리 반장은 동작과 구현 방법은 손대지 않고 구조·이름·중복·죽은
코드만 다루며, 구현 방법을 바꿔야 풀리는 것은 제안으로만 올린다.

## 4단계, 준공 검사와 인수 (`sas-prp-pr`)

모든 공정이 `complete` 가 되면 시공사가 준공 검사를 한다. `sas-audit-code --full` 로 브랜치 전체를
감사하고 결함을 고쳐 커밋한 뒤 PR 을 만든다. 원격 저장소가 없으면 로컬에서 머지한다. 발주자는 PR
을 검토하고 머지하는 것으로 인수한다. 계약서 작성과 마찬가지로 이 단계는 발주자가 직접 시작한다.

## 흐름을 지탱하는 규칙

- **커밋은 시공사만 한다.** 사전 조사팀, 설계 기준 담당, 완전성 검수팀, 검사 기준 팀, 시공팀,
  마감 정리 반장, 검수자는 커밋하지 않는다.
- **규격과 구현은 다른 사람이 정한다.** 린트·정적 분석·테스트로 강제할 수 있는 규칙은 설계 기준
  담당의 몫이고, 그 규칙 안에서 어떤 구조로 만들지는 시공팀과 마감 정리 반장의 몫이다.
- **검사 도구는 두 번 검토된다.** 설계 기준 담당이 계약 단계에서 정하고, 검사 기준 팀이 현장에서
  놓친 것이 있으면 "테스트는 이렇게 만들었지만 이 도구가 더 맞다"고 권장을 올린다.
- **계약 서류는 임시다.** PRD, 부속 서류, plan 은 기능이 끝나면 아카이브로 옮겨진다. 그래서
  코드와 주석은 이 문서들을 가리키지 않고 필요한 배경을 직접 담는다.
- **막히면 멈추고 묻는다.** 사양이 없거나 검사 환경이 없으면 추측으로 채우지 않고 선행 작업으로
  분리해 발주자에게 돌려준다.

## 비유 밖의 두 가지

- **`sas-prp-flow`.** 공정표를 읽어 지금 어디까지 왔는지 판정하고, 발주자가 고른 방식대로 2단계와
  3단계를 공정마다 대신 불러 준다. 계약서 작성과 준공 검사는 부르지 않는다.
- **`sas-file-cleanup`.** 인수가 끝난 계약 서류를 보관함으로 옮기고, 앞으로도 남겨야 할 결정은
  메모리에 옮겨 적는다.

## 예시로 따라가기

발주자가 "로그인 화면에 소셜 로그인을 붙여 달라"고 했다고 하자.

1. 시공사가 요구를 정리해 컨펌받는다. 어떤 제공자를 붙일지, 기존 세션 방식은 유지하는지, 범위
   밖은 무엇인지가 여기서 정해진다.
2. 사전 조사팀이 기존 인증 라이브러리가 소셜 로그인을 이미 지원하는지 확인하고, 직접 구현보다
   나은 대안이 있는지 찾으면서 설계 기준 담당도 함께 불러 기존 인증 모듈과 통일할지 새
   라이브러리를 들일지 선택지를 내놓는다. 발주자가 고른다. 조사 근거는 `research.md` 에 남는다.
3. PRD 에 방향과 공정이 적히고, 제공자별 토큰 필드 같은 세부는 `data-model.md` 에 남는다.
4. 완전성 검수팀이 컨펌한 내용과 조사 근거가 PRD·부속 서류에 빠짐없이 담겼는지 확인한다.
5. 첫 공정의 plan 이 쓰이고, 현장에서 RED, GREEN, 검수, 마감 정리, 공정 검사, 완료 보고가 이어진다.
6. 모든 공정이 끝나면 준공 검사를 거쳐 PR 이 열리고, 발주자가 검토해 머지한다.
