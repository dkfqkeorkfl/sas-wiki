# sas-visual-recipe

P3 recipe+rubric 단일 파일(`docs/qa/dev/<name>.md`)을 **작성하고 수정한다**. recipe 파일을 만들거나 고치는 유일한 통로가 이 스킬이다. 다른 스킬·에이전트·구현 주체는 recipe 를 직접 편집하지 않고 이 스킬을 부르며, 그래야 수정 뒤에도 검증 스크립트가 자동으로 돌아 규격과 인용 유효성이 유지된다. 구동·판정은 `sas-visual-judge`의 일이며 이 스킬은 하지 않는다(캡처·Playwright 조작·LLM 판정 전부 범위 밖). "무엇을 검증할지"(P1~P4 중 어디에 배치할지, 이 기능에 P3가 필요한지)도 이 스킬의 일이 아니다 — 그건 호출자(주로 `sas-tdd-guide`)가 정해서 넘긴다. 이 스킬은 "정해진 검증 대상을 규격에 맞고 안전하게 문서화하고 유지하는 것"만 책임진다.

## 트리거

- 다른 스킬/에이전트(주로 `sas-tdd-guide`)가 P3 recipe+rubric 작성을 요청할 때.
- 사용자가 직접 "이 화면 recipe 써줘", "시각 QA 문서 만들어줘"라고 요청할 때 — 이 경우 「입력 계약」의 항목을 사용자에게 직접 물어 채운다.
- 기존 recipe 를 고쳐야 할 때. rubric 기대값 갱신, GREEN 뒤 `TODO: 사용자 확인` 채우기, `sas-visual-judge` 가 남긴 핸드오프(P2-scope 항목 제외 등) 반영, surface·state 추가가 그 예다. 누가 요청하든 recipe 편집은 이 스킬을 거친다.

## 입력 계약 (호출자 → 스킬)

채워야 할 **필드 목록 자체**는 `RECIPE-FORMAT.md`(필수·조건부 필드 전체)가 SSOT다 — 여기서 다시 나열하지 않는다("이름·viewports 두 개만 빠졌다"처럼 부분 나열하면 RECIPE-FORMAT.md가 바뀔 때마다 또 어긋난다). 호출자(또는 직접 호출한 사용자)가 몰라서 "뭘 줘야 하냐"고 물으면(`--help` 취급) RECIPE-FORMAT.md의 canonical 템플릿을 그대로 안내한다.

호출자가 실제로 정해서 넘겨야 하는 건 필드 이름이 아니라 **그 필드를 채울 값을 결정하는 판단**이다:

- 어떤 라우트/화면(target·surfaces)을 볼 것인가.
- surface별로 어떤 상태·트리거(states)가 있는가.
- 6 시각 카테고리별로 무엇을 기대하는가(rubric 기대값). 모르면 `TODO: 사용자 확인`으로 명시(빈 채로 두지 않는다).
- (해당 시) P2가 못 잡는 상호작용 기대값·다국어/테마 필요 여부·비웹 런타임 구동 방식·판정 제외 영역(masking).
- (있으면만) 완성된 코드를 rubric 근거로 쓰고 싶을 때 — 「근거 인용 규율」을 따른다.

이 판단들을 넘기지 못하면(값 자체가 없으면) 추측하지 말고 「산출물」의 BLOCKED 리포트로 멈춘다(단, 사용자가 직접 호출한 경우는 예외로 물어서 채운다).

**수정 요청**은 대상 recipe 경로와 바꿀 내용(무엇을, 왜)을 넘긴다. 바꿀 값을 정하는 판단은 작성 때와 같이 호출자 몫이고, 새 코드 인용을 넣으려면 「근거 인용 규율」을 그대로 적용한다.

## 파라미터

- `--out`: recipe를 쓸 기준 폴더. 기본값 `docs/qa/dev`. 최종 경로는 `<out>/<name>.md`. 기존 recipe 를 수정할 때는 그 파일의 경로를 그대로 쓴다.

## 작성 규약

양식(canonical 템플릿·frontmatter 필드·구조 규칙)은 `RECIPE-FORMAT.md`가 유일한 원본이다 — 여기서 재기술하지 않는다. 작성 전 그 파일을 읽고 그대로 따른다. `--out`으로 받은 폴더에 `<name>.md`로 쓴다.

**기존 recipe 관례 참고**. 이미 이 형식(RECIPE-FORMAT.md)으로 작성된 recipe가 프로젝트에 있으면 그 명명·구성 관례를 참고해 일관되게 쓴다. 단 이건 **내용**(surface 이름, 상태 정의 방식 등)에 대한 참고일 뿐, 파일 구조 자체(frontmatter·섹션 구성)는 예외 없이 항상 RECIPE-FORMAT.md를 따른다 — 이 스킬은 RECIPE-FORMAT.md 모양이 아닌 다른 형식(예: 프로젝트가 이미 쓰는 별개의 시각 QA 도구 설정)을 만들지 않는다. 그런 별개 도구가 이미 있어서 이 스킬 자체를 쓸지 말지를 판단해야 하는 경우는 이 스킬을 부르기 전 단계(호출자)의 결정이다. 사양 자체가 없으면 작성을 보류하고 BLOCKED로 보고한다(날조 금지).

**기존 recipe 수정**. 파일을 읽고 요청된 부분만 바꾼다. 요청 밖의 내용은 표현까지 그대로 둔다. 다만 수정 뒤 검증 스크립트가 요청과 무관한 기존 인용을 무효로 판정하면(코드가 바뀌어 낡은 경우) 그대로 두면 판정이 blocked 되므로, 「근거 인용 규율」 3 과 같은 방식으로 이름·기대값이나 `TODO: 사용자 확인`으로 바꾸고 상태 노트의 변경 내용에 따로 적는다. 구조(frontmatter·섹션)는 수정 뒤에도 RECIPE-FORMAT.md 를 그대로 만족해야 한다.

## 로케일 전환 방식 진단 (`locales` 를 쓰는 recipe 작성 시)

`localeApply`는 package.json 의존성만으로 단정하지 않고 프로젝트의 실제 i18n 설정을 진단해 채운다.

| 감지 신호                                                                                                             | 라이브러리                                      | strategy                                                                                                                |
| --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `next-intl` 의존 + `middleware.ts`/`proxy.ts`(Next.js 16+, `middleware.ts`는 deprecated) · `[locale]` 라우트 세그먼트 | next-intl (Next.js App Router)                  | `route`                                                                                                                 |
| `next.config.js` 의 `i18n.locales`                                                                                    | Next.js 내장 i18n / next-i18next (Pages Router) | `route`                                                                                                                 |
| `i18next` + `i18next-browser-languagedetector`                                                                        | i18next / react-i18next                         | 감지 순서가 프로젝트 설정마다 다름(querystring/cookie/localStorage 등). 실제 init 설정의 `detection.order` 확인 후 결정 |
| 위 없이 `react-intl`/`vue-i18n`/`lingui` 단독                                                                         | FormatJS / Vue I18n / Lingui                    | `store`(전환 함수·상태를 코드에서 확인)                                                                                 |

확실한 근거 없이 strategy 를 추측하지 않는다. **`locales`가 호출자의 선택사항이었을 때만** 확인 안 되면 `locales`·`localeApply` 필드 자체를 recipe 에서 생략한다(로케일 축 없이 작성, 근거 부족을 상태 노트에 남긴다) — 날조보다 축 생략이 낫다. 반면 **호출자가 `locales`를 명시적으로 요청**했는데 근거를 못 찾으면, 조용히 생략하지 않고 BLOCKED로 반환한다(요청받은 검증 범위를 임의로 줄이지 않는다).

## 근거 인용 규율

rubric 근거는 코드보다 **이름·기대값**을 우선한다: `data-testid` 등 DOM 훅 이름, 디자인 토큰 이름, 번역 문구 키, 기대 동작·기대값(구현 방법이 아니라 결과). 이 근거들은 실제 코드가 없어도(GREEN 이전에도) 미리 정할 수 있어 안전하다.

**코드를 직접 인용하려면 다음을 모두 만족해야 한다**:

1. 그 코드가 이번 작업에서 새로 만드는 것이 아니라 **이미 완성돼 존재하는 코드**다(이번 GREEN에서 새로 생기는 코드는 recipe 작성 시점에 존재하지 않으므로 지어내 인용할 수 없다 — 이때는 아래 "가드 없거나 코드가 아직 없으면"을 따라 `TODO: 사용자 확인`으로 비워둔다).
2. 형식은 `` `<파일 경로>#<타입>{<값>}` `` 하나로 고정한다(아래 검증 스크립트가 기계적으로 추출한다). `<타입>`은 다음 중 하나다:
   - `symbol` — 함수·상수 등 이름 하나(예: `` `panelLimits.ts#symbol{PANEL_TYPE_LIMITS}` ``). 값은 공백·괄호 없는 단순 식별자만.
   - `css` — 클래스·토큰 문자열 그대로(예: `` `Button.tsx#css{text-xs text-ink-mute}` ``, Tailwind 임의값 대괄호도 허용: `w-[42px]`).
   - `code` — 표현식·로직을 설명할 때, 그 로직에 등장하는 핵심 식별자 **하나만**(예: `` `AddPanelMenu.tsx#code{isUnlimitedPanelLimit}` ``) — 전체 표현식을 그대로 베끼지 않는다(코드가 조금만 바뀌어도 깨지고, 괄호가 섞이면 형식 경계도 애매해진다).
   - 심볼·클래스명 없이 파일 하나만 언급(예: `` `tokens.css` ``)해도 된다 — 이때는 파일 존재만 확인한다.
     줄번호 인용은 형식과 무관하게 항상 금지한다.
3. 작성 직후 **아래 검증 스크립트로 그 인용이 지금 실제로 유효한지 즉시 확인**한다 — 확인 안 되면 인용을 지우고 규칙 1 예외(코드 없음)와 같은 방식으로 처리한다.

이 즉시 확인은 **일회성**이다 — "지금 맞다"만 증명하지, GREEN·REFACTOR로 코드가 나중에 바뀌어도 계속 맞는지는 보장하지 않는다. 그 지속적 보호(회귀 테스트로 계속 지켜보는 것)는 이 스킬이 아니라 **호출자**(`sas-tdd-guide`의 하네스 진단, 아래 「산출물」의 상태 노트 참조)의 몫이다.

**가드 없거나 코드가 아직 없으면**: 이름/기대값으로 대체하거나, 정밀한 근거가 꼭 필요하면 `TODO: 사용자 확인`으로 비워둔다. GREEN 이후 실제 코드에 맞춰 채우는 것은 REFACTOR 단계에서 이 스킬을 다시 불러 수정으로 수행한다.

## 검증 스크립트

작성이든 수정이든 파일에 손을 댄 뒤에는 항상 `node .claude/skills/sas-visual-recipe/scripts/validate-recipe.mjs <recipe 경로> <프로젝트 루트>`를 실행해 다음을 **형식·존재 여부만** 기계적으로 확인한다(통과/실패만 — 아래 확인 대상 외의 **의미적 타당성**, 즉 내용이 실제로 말이 되는지는 이 스크립트가 보장하지 않는다. 그건 호출자·사용자가 recipe를 다시 읽고 판단할 몫이다):

- frontmatter 필수 필드·`locales`+`localeApply` 동반·`## Recipe`/`## Rubric` 필수 서브섹션·6 시각 카테고리 존재(「RECIPE-FORMAT.md」의 「구조 규칙」과 동일).
- 줄번호 스타일 코드 인용 금지.
- 코드 인용(`` `<파일>#<타입>{<값>}` ``)마다 타입별로 유효성 확인(위 「근거 인용 규율」 2-3 참조): `symbol`/`code`는 식별자 형식 준수 + 해당 파일에 그 식별자가 있는지, `css`는 그 문자열이 파일에 그대로 있는지, 타입 없이 파일만 언급했으면 파일 존재만.

실패하면 사유를 보고 수정 후 재실행한다(반복 한도는 RED 재시도 관례와 동일하게 취급). 이 스크립트는 프로젝트 테스트 러너와 무관하게 항상 실행 가능하다(Node 내장 기능만 사용). `checkCitations` 함수는 다른 곳(호출자가 지속 보호용 가드 테스트를 설치할 때)에서도 그대로 재사용할 수 있도록 export 돼 있다 — 같은 검사를 두 번 구현하지 않는다.

## 자기완결성

PRD·plan.md·handoff 등 저장소 내부 임시 문서를 인용하지 않는다(프로젝트 종료 후 아카이빙·삭제 대상이라 참조가 끊긴다). 공식 문서·표준 스펙 등 외부 권위 있는 출처 인용은 허용한다. 배경이 그 문서들에만 있고 recipe만 읽어서는 복원되지 않으면, 참조 대신 필요한 배경 자체를 recipe에 옮겨 적는다.

- **상태 노트**(호출자에게 반환, 고정 형식):

  ```
  상태: 작성 완료 | 수정 완료 | BLOCKED
  경로: <out>/<name>.md
  변경 내용: 신규 | <수정한 항목. 요청 밖 처리(무효 인용 정리 등)가 있으면 함께 적는다>

  코드 인용: N건(즉시 검증됨) | 해당 없음
  지속 보호: 코드 인용이 있다면, 이후 GREEN·REFACTOR로 코드가 바뀌어도 계속 유효한지는 회귀 테스트가 지켜봐야 한다 — 그 설치 여부는 호출자(sas-tdd-guide 하네스 진단)가 판단한다. `checkCitations`(`.claude/skills/sas-visual-recipe/scripts/validate-recipe.mjs`)를 재사용할 수 있다.
  ```

- **BLOCKED 리포트**(입력 미비·사양 없음 등으로 작성 불가할 때):

  ```
  상태: BLOCKED
  막힌 이유: <무엇이/왜 막혔는지>
  누락 입력: <target/surfaces | states | rubric 기대값 | localeApply 근거 | ...>
  언블록 조건: <무엇이 채워지면 진행 가능한지>
  ```
