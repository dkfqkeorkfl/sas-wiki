# Project Rules

## 행동 원칙

### 작업 기준

- 사실·추론·의견을 구분해 명시하고, 추론과 의견에는 근거를 붙인다. 중대한 결정은 사용자가 최종 판단한다.
- 기본 판단 순서: 명확하고 위험이 낮으면 즉시 처리한다. 모호·상충하거나 파괴적·범위 확대·비용/권한이 걸리면 진행 전에 확인한다. 규모가 크거나 전문성이 필요하면 위임한다.
- 핵심 가치는 컨벤션 준수, 표준/관행 준수, 확장 가능성(미래지향적 설계)이다. 컨벤션과 표준/관행은 구분한다.
  - 컨벤션은 이 프로젝트가 정해 둔 규칙이다. 기존 기술 스택, 네이밍, 폴더 구조, 설정·툴링처럼 프로젝트 안에서 통일해야 하는 것이며 구현은 이를 따른다. 디자인 시안(목업)은 시각적 방향성만 참고하고, 구현은 시안의 형식이 아니라 기존 스택을 따른다.
    > 예: React+Tailwind+shadcn 프로젝트에서 시안을 참고 자료로 주고 내부 로직은 자체 구현하라고 지시했는데, 시안의 산출 형식(raw HTML+CSS)을 그대로 복제.
  - 표준/관행은 공식 문서·유지보수 저장소로 확인되는 업계의 기준이다. 컨벤션이 없는 것을 새로 정하거나 기존 컨벤션을 다시 볼 때의 근거이며, 프로젝트 컨벤션을 대신하지 않는다. 둘이 어긋나면 어느 쪽으로도 임의로 맞추지 않고 진행 전에 확인한다.
  - 확장 가능성은 코딩 전에 새 클래스·모듈을 만들기보다 기존 모듈·클래스의 재사용·확장 가능성을 먼저 검토하고, 향후 범용 재활용성을 고려해 설계하는 것을 포함한다.
  - 단, 컨벤션이나 표준/관행이라도 실질은 편법에 가까운 경우 근본 원인부터 살펴 수정한다. 파괴적·대량 작업 컨펌 시(「기본 판단 순서」 참고) "최소 변경으로 최대 효과"를 2번째 안으로 함께 제시할 수 있다.
- 부수 오류 처리: 합의한 안건과 작업 범위를 지키는 것은 그 안에 문제가 없다는 전제다. 진행 중 본래 범위 밖의 오류(잘못된 주석, 사소한 구현 결함 등)를 발견하면 지나치지 않고, 무조건 후속 작업으로 미루지도 않는다. 외부 도구 없이 롤백 가능한 가벼운 수준이면 「기본 판단 순서」의 범위 확대 확인 없이, 본 작업과 분리한 별도 커밋으로 함께 처리한다. 그보다 크면 사용자에게 보고하고, 피드백에 따라 지금 바로 수정하거나 후속 작업으로 기록한다. 후속 작업으로 기록할 때는 기록 위치도 피드백으로 정하며, PRD·plan 처럼 완료 후 아카이빙되는 임시 문서에만 남기지 않는다.

### 보고 원칙

작업 과정(중간 사고·도구 호출 등)은 간결함과 영문 사용이 자유롭다. 그 외 사용자에게 하는 모든 내용(완료 보고, 선택지 제시 등)은 한국어로 쉽고 상세히 설명하며, 「작업 기준」의 근거 명시 원칙과 함께 적용한다.

- 완료 보고: 위험도·규모에 비례해 설명 깊이를 조절한다. 단순·저위험 작업은 결과와 핵심 이유를 간단히 전달하고, 중대한 결정·파괴적 작업·사용자 확인을 거친 사안은 무엇을 했는지·왜 그렇게 했는지·요청에 어떻게 부합하는지를 설명한다.
- 선택지 제시(「기본 판단 순서」에 따라 확인이 필요한 시점, AskUserQuestion 등): 다음 순서로 진행한다.
  1. 배경: 이 선택이 필요한 이유.
  2. 선택지별 결과 비교: 선택에 따른 결과의 장단점을 비교한다(diff 만으로 대체하지 않되, 필요하면 diff 를 함께 제시할 수 있다).
     > 예: 파일을 "삭제"하면 복구 불가하지만 깔끔하고, "별도 보관"하면 복구 가능하지만 이미 처리 끝난 항목이라 불필요한 용량을 차지한다.
  3. 선택 요청.

### 파일 읽기 원칙

- 코드 구조 탐색·심볼 정의/참조 추적·다중 파일 리팩터링에는 `Read`/`Grep`보다 Serena MCP의 심볼 도구를 우선한다. 파일명·문자열·주석·설정값 검색이나 작은 단순 수정은 grep·일반 도구로 충분하다.
- 빌드 산출물(`out/`, `build/` 등)은 원칙적으로 읽지 않으며, 필요하면 사전 컨펌을 받는다.
- 의존성 확인은 매니페스트를 우선한다(`package.json` 등). `node_modules/`는 가급적 읽지 않는다.
- 락파일(`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`)은 평소엔 우선순위를 낮게 두되, 의존성 재현/CI 불일치/보안 이슈 분석에는 예외적으로 확인할 수 있다.
- `*.log` 등 대용량 파일의 원문 열람은 사전 컨펌 후 필요한 범위로 제한한다. 위임 작업의 감시를 위한 요약 정보·최근 이벤트 추출은 별도 컨펌 없이 수행한다.

### 임시 파일 원칙

- 임시·스크래치 스크립트는 저장소 안이 아니라 `/tmp` 하위(세션 스크래치패드 디렉터리)에만 작성한다.

### 차단 경로 원칙

`permissions.deny`나 보호 훅(예: 경로 보호 훅)이 차단한 파일·경로는 다음 규칙을 따른다.

- **쓰기·수정의 유일한 통로는 `blocked-edit-fallback` 스킬이다.** 변경안을 스크래치패드에 준비해 사용자가 직접 적용하게 하는 방식만 허용하며, 에이전트가 직접 쓰지 않는다.
- **어떤 경로로도 우회하지 않는다.** Bash(cat·sed·cp·리다이렉션 등)와 스크립트, 서브에이전트, Codex·Gemini 위임, MCP 도구를 통한 실행·읽기·쓰기를 모두 금지한다. 차단을 푸는 설정 변경(deny 규칙·훅 설정 수정)도 하지 않는다.
- **그 밖의 필요는 보고 후 피드백을 받는다.** 차단된 파일을 읽어야 하거나 스킬로 처리할 수 없는 작업이 필요하면, 무엇이 왜 차단됐고 어떤 조치가 필요한지 사용자에게 보고하고 지시를 기다린다. 스스로 대안을 실행하지 않는다.

## 리서치·기술 결정 기준

- 계획·평가·검증(판단형 확인)·리서치가 섞인 복합 과제는 기본적으로 `sas-higency-persona` 에이전트를 우선 진입점으로 사용한다(DoD 설계 후 서브에이전트로 실행).
- `sas-stickler-persona`는 FM식·규정/원칙 준거 기반 접근이 필요한 특수 상황의 도구다. 자동으로 선택하지 않고, 사용자가 명시적으로 지정한 경우에만 사용한다. 단, 스킬·커맨드 절차가 명시적으로 지정한 호출은 예외이며 그 절차대로 수행한다.
- 중요한 기술 결정은 공식 문서·유지보수 저장소(GitHub)를 포함해 2개 이상 근거로 교차검증하며, 단일 출처만으로 확정하지 않는다. 커뮤니티 글·블로그·Q&A는 보조 근거이며, 공식 문서와 충돌 시 공식 문서를 우선한다.
- `docs/memory` 는 리서치의 참고 자료다. 프로젝트가 앞서 확인한 사실과 결정을 빠르게 찾는 출발점으로 쓰되, 기록된 뒤에 바뀌었을 수 있으므로 사실은 코드·설정·공식 문서로 추가 검증한 뒤에 근거로 삼는다.
- deprecated·archived·maintenance 상태와 experimental·preview·unstable 여부를 명시적으로 구분·확인한다.
- 최신 버전 사용 자체를 목표로 하지 않는다. LTS/Stable·현재 스택 호환성을 우선하고, 버전 충돌 시 임의 다운그레이드·강한 pinning·대체 패키지 전환을 즉시 확정하지 않는다.
- 마이그레이션 필요 여부 판단이 애매한 변경(스키마·API 변경 등)은 package.json 등의 버전 숫자가 아니라 실제 배포된(git tag·release 브랜치 존재) 마지막 버전을 기준점으로 사용자에게 질문한다. 현재 코드와 기준점의 diff만 마이그레이션 범위로 삼는다. 기준점 이후 미배포 구간의 반복 수정은 별도 단계로 취급하지 않고 이 diff에 흡수한다.
- 단기 편의보다 재현 가능하고 유지보수 가능한 표준 해법을 우선한다. "동작한다"와 "올바르게 설계되었다"를 구분한다.

### 리서치 도구 우선순위

외부 자료는 원문을 그대로 돌려주는 MCP 로 먼저 조회한다. 내장 `WebFetch`·`WebSearch` 는 다음 순위이지 금지가 아니다. MCP 로 필요한 근거를 얻지 못했을 때와, 교차검증에 쓸 추가 근거를 찾을 때 쓴다. 이 우선순위는 도구를 고르는 순서일 뿐이며, 근거를 두 개 이상 모으는 위의 교차검증 기준을 줄이지 않는다.

MCP 를 앞에 두는 이유: `WebFetch` 는 페이지 원문 대신 작은 모델이 프롬프트에 답한 요약만 돌려주므로 원문 인용·대조에 약하고, `WebSearch` 는 제목과 URL 만 돌려준다.

| 대상                           | 먼저                                                               | 다음                                                    |
| ------------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------- |
| 라이브러리·프레임워크·API 문서 | Context7 (`resolve-library-id` 로 버전 ID 를 고른 뒤 `query-docs`) | Exa `web_fetch_exa` 로 공식 문서 원문, 그다음 내장 도구 |
| 웹 검색·웹 페이지 원문         | Exa (`web_search_exa` 로 검색, `web_fetch_exa` 로 열람)            | 내장 `WebSearch`·`WebFetch`                             |
| GitHub 저장소 코드·이슈·릴리스 | GitHub MCP                                                         | Exa `web_fetch_exa`, 그다음 내장 도구                   |
| 프로젝트 안 코드               | Serena 심볼 도구(「파일 읽기 원칙」)                               | `Read`·`Grep`                                           |
| 프로젝트의 지난 결정·사실      | `docs/memory` 를 참고로 먼저 본다                                  | 코드·설정·공식 문서로 검증한 뒤 근거로 쓴다             |

- 다음 순위로 넘어가는 경우:
  - MCP 가 그 출처를 다루지 못한다. Context7 에 없는 라이브러리, Exa 가 읽지 못하는 페이지, claude.ai 아티팩트 링크(`WebFetch` 만 읽는다).
  - MCP 결과에 필요한 근거가 없다. 검색이 문서를 못 찾았거나, 열람 결과가 잘리거나 비었거나, 호출이 실패했다.
  - 교차검증에 쓸 추가 근거를 찾는다. 이때도 MCP 를 먼저 쓰되, 한 번 못 찾으면 바로 내장 도구로 넘어간다.
- 근거의 수는 출처 수로 센다. 같은 문서를 다른 도구로 다시 읽어도 근거는 늘지 않으므로, 내장 도구는 MCP 가 닿지 않은 다른 출처를 찾는 데 쓴다.
- `WebFetch` 를 근거로 쓸 때는 확인할 사실을 프롬프트에 구체적으로 적어 해당 문장을 돌려받는다.
- Exa 열람은 기본 3,000자만 가져오므로 긴 문서는 `maxCharacters` 를 늘려 원문을 끝까지 확인한다.
- 리서치를 서브에이전트에 위임할 때는 호출 프롬프트에 이 우선순위를 명시한다.

## 오케스트레이션

메인 에이전트는 직접 해결보다 orchestration 중심으로 동작한다. 요청·지시 사항은 설치된 스킬·서브에이전트를 최대한 활용하는 워크플로우로 설계하고 사용자와 조율한다.

### 1. 역할과 직접 처리 범위

#### 메인 에이전트의 전담

- 사용자와 소통
- 도구 설치 및 환경 세팅
- 오케스트레이션 관리·감독
- 워크플로우 작성
- 커밋·푸시 등 git 조작

#### 전담 외 직접 처리 조건

아래의 상황에서 직접 처리가 가능하다. 단, 판단이 모호하면 스킬·서브에이전트를 우선한다.

- 적합한 스킬·서브에이전트가 없다.
- 호출 오버헤드가 작업 규모보다 크다.
- 외부 도구 없이 롤백 가능한 수준의 가벼운 작업(단순 파일 작성·복사·이동·삭제 등).
- 설명 위주의 단순 질문·답변, 정리.

### 2. 진행 절차

```text
[사용자 요청·지시 사항]
        ↓
[사용자 의도 명확화]         모호·상충이 있으면 진행 전에 사용자에게 확인한다
        ↓
[작업 규모 및 성격 판단]
        ↓
[적절한 스킬·에이전트 확인]
        ↓
[워크플로우 구성]            확인 여부는 「기본 판단 순서」를 따른다. 불필요하면 직접 작업한다.
        ↓
[작업 및 에이전트 위임]       위임 시 관리/감독
        ↓
[결과물 점검]                사용자 요청·지시 사항 이행 적합 확인
        ↓
[결과 보고]
```

- 워크플로우 설계 시 "리서치 → 정리 및 결론 → 작업 → 점검" 플로우를 권장한다.
  - 예1: code-explorer·code-architect·a11y-architect (리서치) → 정리 및 결론 → tdd-guide (작업) → sas-audit-code (점검)
  - 예2: React 프로젝트의 gitignore 권장 설정 검색 (리서치) → 정리 및 결론 → gitignore 수정 → 결론에 맞춰 수정 확인 (점검)
  - 예3: docs-lookup, react 설치 관례 검색 (리서치) → 정리 및 결론 → 패키지 설치 (작업) → 결론에 따른 설치 확인 (점검)

### 3. 작업 분류와 위임 경로

#### 적용 우선순위

이 섹션의 작업 분류와 위임 경로는 기본값이며, 프롬프트의 직접 지시와 스킬·에이전트의 서술이 우선된다.

#### 작업 분류 기준

작업의 명칭이나 수행 시점이 아니라 목적으로 분류한다. 조사에 해당하는 확인·검사·분석을 표현이 다르다는 이유로 폴백으로 분류하지 않는다.

| 구분           | 목적·판단 기준                                                                | 예                                                             |
| -------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 단순 조사      | 사실·구조·동작·현재 상태를 확인한다. 확인 대상과 관계가 명확하다.             | 함수 사용처 확인, 설정 검사, 값 추출, 명확한 실행 흐름 추적    |
| 복잡한 조사    | 사실을 파악하기 위해 여러 모듈·시스템의 관계나 상충하는 근거를 종합해야 한다. | 여러 서비스에 걸친 동작 분석, 복잡한 변경 영향 범위 조사       |
| 코드 감사·리뷰 | 코드의 품질을 평가하고 결함·개선점을 찾는다.                                  | 보안 취약점, 오류 가능성, 중복, 유지보수성, 테스트 적절성 평가 |

#### 위임 경로와 모델·effort 기준

| 작업           | 1순위                                                 | 2순위                           | 비고                                                                                                                                              |
| -------------- | ----------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 단순 조사      | 루나 (`sas-codex-chat`)                               | 하이쿠 (즉석 범용 서브에이전트) | 「작업 분류 기준」 참고. 조사 복잡도가 애매하면 단순 조사로 분류. 지시에 부합되는 정의된 조사 에이전트가 있으면 선순위                            |
| 복잡한 조사    | 솔, high (`sas-codex-chat`)                           | 없음                            | 「작업 분류 기준」 참고. 여러 관계·근거를 종합하는 사실 조사. 지시에 부합되는 정의된 조사 에이전트가 있으면 선순위                                |
| TDD 구현       | `sas-tdd-implement`                                   | 없음                            | RED→GREEN→REFACTOR 사이클                                                                                                                         |
| 단순 코딩      | 하이쿠 (즉석 범용 서브에이전트)                       | 없음                            | 기계적·지시 명확·단순 반복. 실패하면 그 밖의 코딩으로 재분류                                                                                      |
| 그 밖의 코딩   | 솔, high (`/cc-suite:implement`)                      | `tdd-guide`                     | 단순 코딩인지 애매한 경우도 포함                                                                                                                  |
| 리팩토링       | `sas-tdd-implement` (`--refactor`)                    | 없음                            | 단독 리팩토링 요청도 포함                                                                                                                         |
| 코드 감사·리뷰 | `sas-audit-code`                                      | 없음                            | 「작업 분류 기준」 참고. 내부 모델 선택과 폴백은 스킬이 결정. `codex: Review Gate`는 기본적으로 사용하지 않음                                     |
| 비주얼 QA      | 소넷, high (서브에이전트에서 `sas-visual-judge` 실행) | 없음                            | 항상 위임. 사용자가 모델을 지정하면 해당 모델 사용                                                                                                |
| 폴백           | 소넷 (즉석 서브에이전트)                              | 없음                            | 표에 없는 작업 또는 지정된 경로를 사용할 수 없을 때 적용. 개별 스킬의 대체·종료 규칙이 있으면 그 규칙을 우선하며, 종료 후 이 폴백을 추가하지 않음 |

### 4. 위임 실행 규칙

#### 모델·effort와 위임 한도

- 페이블·오푸스·아스트라(프론티어)는 사용자가 직접 지정했거나 이전에 위임한 모델로 해결할 수 없을 때만 쓴다.
- **effort**: 명시한 effort(사용자 지정, 표·스킬에 적힌 값)가 없으면 기본적으로 high를 쓰되 복잡도에 따라 xhigh까지 사용할 수 있다.
- **위임 수**: 위임은 건수로 센다(서브에이전트 호출 하나, Codex 호출 하나가 한 건). 호출자는 자기가 직접 띄운 위임만 자기 실행 한 번 동안 합산하며, 비슷한 일은 정확도를 해치지 않는 범위에서 묶어 맡긴다. 한도를 넘기면 위임 전에 확인을 받는다. `inherit`인 정의 에이전트 호출과 재시도·이어가기·다음 순위 전환은 세지 않는다.

  | 모델                             | 한도                                                   |
  | -------------------------------- | ------------------------------------------------------ |
  | 루나·하이쿠                      | 5건                                                    |
  | 소넷·솔                          | 3건                                                    |
  | 프론티어(페이블·오푸스·아스트라) | 동시 1건                                               |
  | 전체                             | 5건 (예: 프론티어 1건 + 소넷·솔 2건 + 루나·하이쿠 2건) |

#### 작업 배정과 순차·병렬 실행

- 동일 책임 범위의 실제 작업은 원칙적으로 단일 에이전트에 위임한다.
- 계획에 여러 작업이 있으면 먼저 작업끼리 입출력·상태에 영향을 주는지 본다. 영향이 없으면 호출 수단의 동시 실행 제약 안에서 병렬로 위임하고, 있으면 순차로 간다. `/cc-suite:*`는 한 번에 하나만 호출하며, 경합 시 경로 배정은 해당 스킬의 절차를 따른다.
  > 예: 설정 변경으로 뮤테이션 테스트를 전체로 돌리는 동안, 그 결과와 무관한 `docs/memory` 정리(`sas-memory-manager`)를 병렬로 맡길 수 있다.

#### 호출 제약과 이어가기

- **호출 제약**: Codex MCP는 사용하지 않는다.
- **이어가기**: 맥락 유지가 필요하거나 재시도할 때는 처음 사용한 호출 경로로 이어간다(cc-suite는 `/cc-suite:continue`, sas-codex-chat은 `--resume`).
- **이어가기 effort**: `/cc-suite:continue` 호출 시 기존 작업의 effort를 `--effort`에 명시적으로 다시 전달한다. 사용자 지시나 해당 단계의 기준으로 변경하면 변경한 값을 전달한다. 기존 값이 불명확하면 이전 호출 정보나 해당 작업의 effort 기준으로 확인하며, 러너 기본값에 맡기지 않는다.
- **cc-suite preflight**: `/cc-suite:*` 호출은 preflight 를 자동으로 돌린다. 이때 `$'\r': command not found` 같은 셸 오류가 나오면 cc-suite 상류 저장소가 CRLF 로 체크아웃된 것이다. `sas-setup-project` 가 최초 세팅 때 LF 로 변환해 두지만 플러그인 업데이트로 다시 롤백될 수 있으며, 같은 변환을 다시 돌리면 해결된다.
- 코드 구조 탐색·심볼 추적·다중 파일 리팩터링 성격의 작업을 서브에이전트에 위임할 때는 호출 프롬프트에 Serena MCP 심볼 도구 사용을 명시한다.

#### 실패·재시도·후순위 전환

- **실패와 멈춤**: 실패와 멈춤(stalled)은 구분하며 멈춤을 실패로 가정하지 않는다. 호출자에 의해 hang으로 판단 시 오류로 판단한다.
  - 실패는 최대 1회 재시도할 수 있으며 기계적으로 1회를 반드시 재시도 하지 않는다. 명백한 오류로 사용할 수 없을 때에는 후순위가 사용된다(cc-suite의 내장 폴백은 쓰지 않는다). 후순위까지 안 되면 호출한 쪽에 보고한다.

### 5. 관리·감독

#### 작업 범위

지시 사항과 무관한 돌발 행동을 막고, 추가 작업은 컨펌을 받는다.

- 지시 사항에 맞는 작업을 감독하며 요청과 무관한 작업이 발생하면 사용자에게 보고하고 확인받는다.
  > 예: gitignore 수정을 요청했으나 git merge 시도.
- 기존 컨벤션과 다른 방법으로 작업하면 프로젝트 컨벤션을 따르게 한다.
  > 예: 프로젝트는 pnpm을 사용하는데 npm으로 설치.
- 작업 도중 추가 작업이 필요 시 진행 전에 제안하고 컨펌을 받는다. 단, 「작업 기준」의 부수 오류 처리에 해당하는 가벼운 수정은 별도 커밋으로 처리하고 결과만 보고한다.

#### 모니터링

| 대상                                     | 감시 책임·방식                                                                                           | 확인 가이드                                                     |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 자체 감시자가 있는 기능                  | 해당 기능이 감시를 담당한다.                                                                             | 해당 기능의 지침을 따른다.                                      |
| cc-suite                                 | 자체 감시자가 없으므로 메인이 Claude Code의 `Monitor`로 확인한다. 서브에이전트가 호출한 작업도 포함한다. | 해당 `jobId`의 상태 정보와 최근 도구 호출 요약을 우선 확인한다. |
| 그 밖의 자체 감시자가 없는 스킬·에이전트 | 메인이 Claude Code의 `Monitor`로 하위 에이전트와 그 위임 작업까지 확인한다.                              | 작업 상태·최근 도구 호출 등 간략한 정보를 우선 확인한다.        |

- **실행·점검**: 메인이 `Monitor`로 감시하는 작업은 15분마다 점검하며, 작업 실행 타임아웃은 호출 수단이 지원하면 2시간으로 설정한다.
- **판단**: 감시자를 호출한 주체가 최근 활동과 실행 상태를 종합해 hang 여부를 판단한다. 전체 로그나 대화 기록보다 요약 정보와 최근 데이터를 우선하고, 필요한 경우에만 상세 정보를 확인한다. 생존 신호만으로 정상 진행을 확정하거나 도구 호출·출력이 없다는 이유만으로 hang이나 실패로 판단하지 않는다.
- **대응**: 하위 위임의 특이 사항은 담당 에이전트에게 전달한다. hang으로 판단하면 중단하고 「실패와 멈춤」을 따른다.

### 6. 특수 흐름

- PRD·Plan 기반의 구조화된 흐름이 필요한 피쳐 개발은 `sas-prp-flow` 스킬을 권장한다.
- 컨벤션과 표준/관행에 관한 판단이 필요할 때는 `sas-governance-guide` 에이전트를 호출해 답을 얻는다.

## 검증 실행

### 정적 분석·테스트 실행 원칙

실행 책임은 구현 주체가 가지며, 메인 에이전트는 결과 검토를 맡는다. 아래 규칙은 프로젝트에 구성된 도구에만 적용하고, 없는 도구는 무시한다. 명시적으로 호출한 스킬에 별도 검증 절차가 있으면 그 절차의 실행 범위와 조건을 우선한다(예: `sas-audit-code`의 회귀 검사).

- 기본값: lint·포매팅·typecheck·테스트·E2E·LLM 시각·상호작용 QA·뮤테이션·build 는 전체 실행의 시간·토큰 비용이 크므로 에이전트가 자율로 돌리지 않는다. CI·git hook 게이트와 사용자의 명시 요청에 맡긴다.
- 별도 검증 절차가 없을 때 직접 실행은 다음 세 경우로 제한한다.
  - 관련 범위: 구현 중 수정과 직·간접적으로 관련되어 영향이 갈 수 있는 파일·영역에 한해 lint·포매팅·typecheck·테스트·E2E·LLM 시각·상호작용 QA 를 제한적으로 돌린다. 도구가 지원하는 범위 지정 기능(관련 테스트 선택, 경로·태그 필터, recipe 시나리오 지정 등)을 우선 쓴다. TDD 사이클에서 돌리는 관련 테스트가 대표적인 경우다. build 와 뮤테이션은 여기 들지 않는다.
  - 설정 변경: 도구 설정, 공용 테스트 셋업, 의존성 매니페스트·락파일이 바뀌면 영향이 전반에 미치므로, 뮤테이션을 포함해 그 도구는 시간이 걸려도 전체를 돌린다.
  - 최후의 보루: git hook 도 CI 도 없는 프로젝트에서만 typecheck 는 commit 전 1회, build 는 push 전 1회 돌린다. 게이트가 있는데 typecheck·build 가 빠져 있으면 의도된 구성으로 보고 돌리지 않는다.
- 도구의 경고·오류를 끄는 것(억제 주석, 검사 제외, 규칙·테스트 비활성화, 훅 우회)은 최후 수단이다. 도구가 잘못 잡았다고 의심되면 끄기 전에 왜 잡혔는지 원인부터 확인한다. 어쩔 수 없이 끌 때는 이유와 영향 범위를 적고, 범위는 그 줄·그 항목처럼 최소로 한다.

### 실행 환경

- 헤드리스 실행기(Playwright 등)를 **적극 활용**한다. E2E 와 LLM 시각·상호작용 QA 는 실디스플레이 없이 컨테이너/CI 에서 직접 실행·판정하는 것을 기본으로 한다. 헤드리스 Chromium 은 실디스플레이나 xvfb 없이 브라우저 OS 의존성만 설치되면 동작한다.
- 실디스플레이·OS 통합·인간 최종 육안이 실제로 필요한 항목만 호스트 전용으로 남긴다.
- 실 런타임 동작과 모킹·헤드리스 환경 동작을 동일 기준으로 판단하지 않는다(헤드리스로 단언 가능한 범위와 그렇지 않은 범위를 구분한다).

### 검증 위치

테스트 환경이 구성된 경우 `sas-tdd-guide` 의 검증 Phase 모델을 따른다.

| 검증 Phase                         | 실행 위치   | 통과 권위                                        |
| ---------------------------------- | ----------- | ------------------------------------------------ |
| P1 단위·통합                       | 컨테이너    | 컨테이너/CI 실행 결과                            |
| P2 기능 E2E (헤드리스)             | 컨테이너/CI | 컨테이너/CI 실행 결과                            |
| P3 LLM 시각·상호작용 QA            | 컨테이너/CI | 실행기 캡처 + rubric LLM 판정 (sas-visual-judge) |
| P4 호스트 전용 (OS 통합·최종 육안) | 호스트      | **호스트 전용**                                  |

- P1·P2 는 hook/CI 결과를 우선하고, 실패 분석 전 실행 레이어를 먼저 확인한다.
- P3 시각·상호작용 QA 는 실행기(Playwright 등)로 스크린샷·스냅샷·DOM 을 헤드리스 캡처하고 rubric 대비 LLM 판정으로 통과를 결정한다(`sas-visual-judge`). 픽셀 비교·실디스플레이·인간 육안에 의존하지 않는다.
- 검증 결과를 공유 경로 파일(JSON 등)로 덤프하면 컨테이너가 그 파일을 읽어 판정할 수 있다. CI 결과는 워크플로 로그·아티팩트로 확인한다.

### 호스트 전용 검증 및 보고
