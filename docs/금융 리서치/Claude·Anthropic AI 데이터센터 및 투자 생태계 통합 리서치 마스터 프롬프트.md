# Claude·Anthropic AI 데이터센터 및 투자 생태계 통합 리서치 마스터 프롬프트

## 0. 목적

아래의 대화 기반 자료를 바탕으로 **Anthropic/Claude의 성장, AI 데이터센터 수급, 관련 기업의 수혜·위험, xAI/SpaceX와 Tesla까지 연결되는 AI 인프라 투자 구조​**를 하나의 완성된 리서치 보고서로 재구성하라.

이 작업은 단순 대화 요약이 아니다.

최종 목표는 다음 질문에 답하는 것이다.

> Claude/Anthropic의 실제 사용량과 매출이 빠르게 증가하고 있다는 가설이 데이터센터 증설·임대·컴퓨트 구매 계약을 통해 얼마나 뒷받침되는가?  
> 이 수요 증가에서 경제적 이익을 가장 직접적으로 흡수하는 상장기업 또는 인프라 사업자는 누구인가?  
> 반대로 현재 AI 데이터센터 투자가 향후 과잉공급·감가상각·전력 병목·고객 집중 위험으로 전환될 가능성은 어느 정도인가?

결과물은 장기간 보관할 수 있는 **투자·산업 리서치 보고서** 형식이어야 한다.

중간 사고과정이나 역할극 대화는 출력하지 않는다.

# PART A. 최초 문제의식 — Claude Code가 느려졌다

사용자가 Claude Code를 장시간 사용하면서 다음 변화를 체감했다.

과거에는:

- 5시간 사용 제한을 상당히 빠르게 소진
- 이후 제한이 풀릴 때까지 쉬는 일이 자주 발생

최근에는:

- 아무리 사용해도 5시간 제한을 끝까지 쓰기 어려움
- 반면 주간 사용량은 과거보다 빠르게 감소
- 현재 주간 사용량에는 약 50% 프로모션 증가분이 적용되어 있음
- 결과적으로 단기 5시간 제한이 아니라 주간 제한이 실질적인 병목으로 변화

사용자의 핵심 가설:

> Claude Code 자체의 응답속도가 과거보다 상당히 느려져 동일한 5시간 동안 수행할 수 있는 작업량이 감소한 것이 아닌가?

대화에서는 이 현상이 개인 체감만은 아닐 가능성이 높다는 방향으로 논의됐다.

### 5시간 제한과 주간 제한

두 제한은 동일한 타이머가 아니라 서로 다른 사용량 제약으로 이해했다.

- 5시간 창: 단기 세션별 사용량 제한
- 주간 제한: 더 긴 기간에 걸쳐 누적되는 사용량 제한

서버 응답이 느려지면 동일한 벽시계 5시간 동안 실행할 수 있는 요청 수가 감소한다.

따라서:

> 5시간 제한은 남아 있는데 주간 사용량은 계속 줄어드는 현상

자체는 논리적으로 가능하다.

# PART B. Claude Code 지연의 원인 후보

대화에서는 다음 네 후보를 검토했다.

### 1. 사용자 증가 + 사용자당 컴퓨트 증가

가장 유력한 후보로 평가했다.

단순히 Claude 사용자가 늘어난 것뿐 아니라 Claude Code가 일반 Chat보다 훨씬 많은 연산을 소비한다.

Claude Code 작업은 대략:

사용자 명령  
→ 프로젝트 탐색  
→ 여러 파일 읽기  
→ 추론  
→ 코드 수정  
→ 테스트  
→ 로그 분석  
→ 재수정  
→ 재테스트

의 에이전트 루프를 반복한다.

따라서 일반 채팅 이용자 증가보다 Claude Code 이용자 증가가 데이터센터 수요에 훨씬 큰 영향을 줄 수 있다.

### 2. 사용 가능한 AI 가속기 슬롯 부족

서비스 측면에서 가장 직접적으로 지연을 만드는 요인으로 추정했다.

요청:

라우팅  
→ 가속기 할당 대기  
→ Prefill  
→ Decode  
→ Tool 실행  
→ 다시 모델 호출

구조이므로 Claude Code처럼 한 작업에서 모델 호출이 반복되면 작은 대기시간도 누적된다.

### 3. 모델·하네스·추론방식 변화

사용자가 중요하게 본 부분이다.

단순 서버 대기만 증가했다면:

- 응답시간은 길어질 수 있지만
- 동일 작업의 주간 사용량까지 더 빨리 줄어드는 것은 충분히 설명되지 않는다.

따라서 최근 Claude Code가:

- 더 많은 파일을 탐색하거나
- 사고 토큰을 더 많이 쓰거나
- Tool call을 더 많이 수행하거나
- 검증·재시도를 더 많이 하거나
- 컨텍스트를 더 많이 재처리

하도록 하네스 또는 모델 행동이 변했다면

`응답 지연 + 주간 사용량 증가`

두 현상을 동시에 설명할 수 있다.

### 4. 네트워크·지역 라우팅

부분적인 원인은 될 수 있으나 전체 현상을 설명하는 주원인으로 보기는 어려운 것으로 판단했다.

# PART C. 하드웨어 병목 — GPU인가 HBM인가

사용자가 말한 “RAM”은 일반 DDR RAM이 아니라 HBM이었다.

대화에서 최종적으로 다음과 같이 구분했다.

## 서비스 전체 병목

가장 중요한 것은:

> 실제로 즉시 사용할 수 있는 AI 가속기 클러스터의 총량과 스케줄링 용량

이다.

## 개별 추론 병목

Claude Code처럼 긴 컨텍스트에서는:

- HBM 용량
- HBM 대역폭
- KV Cache
- Prefill 연산
- 칩 간 네트워크

가 중요하다.

### Prefill

긴 코드·대화·Tool 결과를 처음 읽는 구간.

상대적으로 Compute-bound 특성이 강하다.

### Decode

토큰을 순차 생성하는 구간.

상대적으로 HBM 대역폭과 KV Cache 접근의 영향을 크게 받는다.

### 긴 Claude Code 세션

컨텍스트가 커지면:

- Prefill 연산 증가
- KV Cache 증가
- HBM 점유 증가
- 한 가속기에 수용할 수 있는 동시 요청 감소
- Decode 비용 증가

가 동시에 발생한다.

그러나 대화의 중요한 결론은:

> HBM 하나만의 병목이라기보다  
> HBM + 가속기 + 전력 + 냉각 + 네트워크까지 완성되어  
> 즉시 Claude를 돌릴 수 있는 완성형 컴퓨트 용량의 부족

이 현재 현상을 더 잘 설명한다는 것이었다.

# PART D. 데이터센터 계약을 역추적한 이유

사용자는 단순한 하드웨어 이론보다 Anthropic이 실제로 어떤 데이터센터·클라우드 용량을 확보하는지를 역추적하면 수요 증가를 더 잘 추정할 수 있다고 판단했다.

핵심 아이디어:

> Anthropic이 어떤 종류의 컴퓨트를, 어느 정도 규모로, 얼마나 급하게, 어떤 가격에 확보하는지를 보면  
> 현재 부족한 자원이 무엇인지와 실제 수요 증가 속도를 간접적으로 읽을 수 있다.

이 접근을 보고서의 핵심 분석방법으로 유지한다.
