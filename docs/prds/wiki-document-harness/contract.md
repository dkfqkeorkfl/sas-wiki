# 위키 검사 체계의 합의 목표

이 문서는 대화에서 조율한 구조·동작·성공과 실패 기준의 **현재 목표 설계**다. 조사·구현에서 더 적합한 구조나 제약이 드러나면 이유와 영향을 확인하고 조율해 갱신한다. 작업 순서·현재 상태는 [prd.md](prd.md), 파일별 구현·이전·검증 방법은 각 페이즈의 plan.md가 소유한다.

## C1. 구성 요소와 책임

| 구성                   | 책임                                                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 기능 스크립트          | summary·feeds·wiki 조회와 산출물 생성. scripts에 둔다                                                                                |
| 스크립트 테스트        | 기능의 정상·실패 동작과 출력 계약 검증. scripts의 대상 옆에 둔다                                                                     |
| 문서 집행 테스트(가드) | 실제 wiki 문서 전체에 작성 규칙과 무결성 규칙 적용. harness/wiki-documents가 소유한다                                                |
| 하네스 테스트          | 가드·검사기에 정상/위반 입력을 주어 검출 기능과 수집·실행 연결의 회귀를 검증. 같은 분야의 `harness/wiki-documents/__tests__/`에 둔다 |
| 빌드                   | 검증한 커밋의 환경별 summary·feeds 생성                                                                                              |
| 향후 린트              | 코드·테스트 품질을 위한 별도 분야. 이번 작업에서 도입하지 않는다                                                                     |

실제 문서의 오류를 잡는 검사와 그 검사 장치가 정상인지 확인하는 회귀 검증을 구분한다. 일반 스크립트 기능 테스트를 수동 회귀로 옮겨 자동 집행 범위에서 제외하지 않는다.

## C2. 목표 폴더와 네이밍 원칙

```text
sas-wiki/
  scripts/
    summary.mjs
    feeds.mjs
    wiki.mjs
    lib/
      ...기능에서 사용하는 공통 코드
      __tests__/
    __tests__/
    test-utils/
  harness/
    wiki-documents/
      ...문서 검사 코드가 필요한 경우 그 책임에 맞는 모듈
      __tests__/
        document-rules.guard.test.mjs
        document-rules.test.mjs
        ...문서 집행의 회귀·수집·훅·CI 연결 계약
    test-utils/
  docs/prds/wiki-document-harness/
    prd.md
    contract.md
    P1.document-enforcement/
      plan.md
    ...실제로 계획을 작성한 페이즈
```

하네스는 `harness/<분야>/`의 두 번째 깊이에서 구분한다. 테스트는 각 대상 폴더의 `__tests__/` 바로 아래에 두고 그 안에 하위 폴더를 만들지 않는다. 위 구조는 현재 합의한 목표안이다. 조사·구현에서 변경이 필요하면 C10에 따라 반영한다. 파일 수·검사 함수 이름은 계획에서 정하고 필요 없는 빈 폴더를 만들지 않는다.

문서 검사·린트 같은 검사 분야로 구분하며, 집행·회귀 또는 자동·수동 실행이라는 이유로 분야를 다시 나누지 않는다. 같은 문서 검사 분야의 가드·동작 회귀·설정 계약은 `wiki-documents/__tests__/`에 함께 둔다. 종류는 파일명의 접미로, 실행 범위는 Vitest 수집 설정으로 구분한다.

폴더명·파일명·테스트 종류와 의미는 `/workspace/docs/prds/convention-harness-unification/rules.md` 및 `decisions.md`를 그대로 따른다. 이 저장소에 맞추는 범위는 하네스 루트를 `harness/<분야>/`로 구성하는 배치, 기존 `.mjs` 확장자, 검사 장치 회귀의 수동 실행 정책이다. 이 차이를 다른 명명·분류 규칙의 예외로 확대하지 않는다.

| 기준        | 적용                                                                                                                                                                                                                                                                           |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R-B1·R-B4   | 일반 모듈 camelCase, 폴더와 하네스 파일 kebab-case. `__tests__`·`__fixtures__`는 예외. helpers 폴더 금지                                                                                                                                                                       |
| R-B2a       | `<대상>(.<역할>)?(.<주제>)*(.<종류>)*.test.mjs`. 역할은 helpers, 종류는 render·contract·source-scan·guard·seam·flow·build·i18n·a11y. source-scan은 맨 끝. 일반 주제 camelCase, 하네스 주제 kebab-case                                                                          |
| R-B2b·R-B2c | 단일 소스 테스트는 소스와 대소문자까지 일치. 다중 소스는 확인하는 일로 명명. 하네스의 대상 이름 예외는 유지. 계획 단계·진행 이력 식별자를 테스트 파일·제목에 넣지 않음                                                                                                         |
| R-N13·R-N16 | 기능 전용 코드는 기능 옆, 실제 복수 소비처가 있을 때 공용으로 분리. 한 기능의 보조 함수 모음은 `<이름>.helpers.mjs`. 책임 이름이 있는 모듈을 일괄 helpers로 개명하지 않음. 의미 없는 util/helpers 파일 금지                                                                    |
| R-N14·R-N15 | 테스트는 대상 분야 옆 `__tests__/` 바로 아래에 종류 구분 없이 모은다. 단일 테스트 파일 전용 도우미는 파일 내부, 두 개 이상의 테스트 모듈이 공유하면 `scripts/test-utils/` 또는 `harness/test-utils/`. `__tests__` 안 도우미 파일 금지. 제품 코드에서 테스트 도우미 import 금지 |
| R-N17       | 원문 검사에는 관련 source-scan 이름·범위 규칙 적용. 하네스의 예외 유지                                                                                                                                                                                                         |
| R-N18       | 보호된 하네스 소유 원칙 유지. 이 저장소에서는 harness 아래 분야별로 적용                                                                                                                                                                                                       |

정적 테스트 데이터는 대상 옆 `__fixtures__/`에 둔다. 스크립트 테스트와 하네스 테스트의 도우미 소유를 구분하며, 기능 테스트가 보호 폴더의 도우미에 의존하지 않게 한다. 이번 변경과 무관한 기존 파일 전수 개명과 TypeScript 전환은 하지 않는다.

종류 접미의 의미도 부모 `decisions.md` 5절의 정의를 따른다. 하네스 폴더에 있다는 이유로 종류를 하나로 정하지 않는다.

| 검사 목적                                            | 종류·이름 예시                                  | 실행 범위         |
| ---------------------------------------------------- | ----------------------------------------------- | ----------------- |
| 실제 wiki 전체를 훑어 작성 규칙·무결성 위반 검출     | `document-rules.guard.test.mjs`                 | 자동 제품 test    |
| 가드·검사기에 정상/위반 입력을 주어 동작·검출력 확인 | `document-rules.test.mjs` — 별도 종류 접미 없음 | 수동 test:harness |
| 수집 범위·설정·Git 훅/CI 연결 같은 약속 확인         | `test-selection.contract.test.mjs`              | 수동 test:harness |

예시의 구체 이름은 대상과 검사 책임에 맞춰 계획에서 정한다. `.guard`는 여러 파일·저장소의 위반 검출, `.contract`는 설정·데이터 모양·타입·연결의 약속 잠금이다. 가드의 동작을 시험하는 테스트를 다시 `.guard`로 분류하거나 모든 하네스 테스트에 `.contract`를 붙이지 않는다. 새 종류로 harness·regression 접미를 추가하지 않는다. 부모의 문법과 의미는 같고, 확장자는 이 저장소의 기존 `.mjs`를 사용한다.

## C3. 테스트 명령과 실행 주체

| 명령          | 포함                                         | 제외                                                        | 실행 시점                      |
| ------------- | -------------------------------------------- | ----------------------------------------------------------- | ------------------------------ |
| test          | 스크립트 기능 테스트 + 실제 문서 집행 테스트 | 검사 장치 회귀 테스트                                       | 개발자·pre-push·CI의 일반 실행 |
| test:coverage | test와 동일한 테스트 + 제품 커버리지         | 검사 장치 회귀·테스트 지원 코드를 제품 계측에 포함하지 않음 | CI·필요시 수동                 |
| test:harness  | 검사 장치의 회귀 테스트                      | 실제 wiki 전량 집행·일반 스크립트 테스트                    | 하네스 설정·개발·변경 시 수동  |

test와 test:coverage의 수집 집합은 같고, test:harness와 겹치지 않는다. test:harness가 실제 문서 전량을 다시 검사하지 않도록 오류 주입은 임시 픽스처에서 한다. 해당 명령이 수집할 테스트를 하나도 찾지 못하면 실패한다. 전체 wiki 입력이 없을 때 문서 집행이 빈 반복문으로 통과하지 않는다. prod의 문서 수가 draft 제외로 0이 되는 것은 그 자체로 오류가 아니다.

`wiki-documents/__tests__/` 안에서 종류 조각에 `.guard`가 있는 집행 테스트만 자동으로 수집하고 나머지 회귀·설정 계약은 수동으로 수집한다. guard 뒤에 다른 종류가 이어지는 파일도 가드로 취급한다. `scripts`의 기능 테스트는 종류와 무관하게 계속 자동 대상이며 `.contract` 자체가 수동 실행을 뜻하지 않는다.

CI·Git 훅·빌드·pretest 등의 간접 호출에서도 test:harness를 자동 실행하지 않는다. 하네스 회귀의 수동 검증 결과는 개발 중 확인하며 자동 제품 게이트에 섞지 않는다.

## C4. 문서 제목·날짜·갱신

- 화면 표시 제목은 `.md`를 제외한 파일명 전체다. 공백·하이픈·`DD. ` 접두도 그대로 사용한다. 폴더 트리의 폴더명은 실제 디렉터리명이다.
- 작성 frontmatter의 title은 사용하지 않는다. API·렌더러 데이터의 title은 유지하고 파일명으로 생성한다. title 제거를 이유로 API 필드를 없애지 않는다.
- TREND·REPORT는 모두 `wiki/{종류}/YYYY-MM/DD. 제목.md` 형식이다. 월 폴더와 파일 날짜는 실제 달력 날짜여야 한다.
- 기존 작성 가이드의 type: concept, `meta.asOf: YYYY-MM-DD`, 첫 본문의 동일한 날짜 기준 안내를 유지한다.
- 새 기준일·새 분석은 새 날짜 문서로 작성한다. 이전 스냅샷을 보존하고 이전 문서와 연결한다. 기존 날짜 파일은 오탈자·사실 정정을 하고 기준일은 유지한다.
- 경로·메타·본문 기준일은 자동 검사한다. 분석의 신규성, 정정과 새 분석의 구분, 연결의 적절성은 가이드·리뷰가 판단한다. 이를 전부 기계적으로 보장한다고 표현하지 않는다.

기존 위키 본문·기존 문서 ID를 이번 검사 체계 재구성을 이유로 변경하지 않는다.

## C5. 문서 집행 범위와 판정

dev에서는 draft를 포함한 전체 문서를 검사하고 prod에서는 draft 제외 후 참조·산출물 정합을 검사한다. 환경별 가시성과 데이터 생성의 규칙은 기능 코드와 공유해 검사 쪽에 다른 사본을 만들지 않는다.

| 검사                                                                             | 목표 판정                                                                  |
| -------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 필수 frontmatter·type·문서 스키마·UUIDv7·금지된 created/updated 직접 작성        | 위반 시 실패                                                               |
| 문서 경로·ID 중복, 기존 ID 사후 변경, 삭제 ID 재사용, 문서로 파싱되지 않는 stray | 위반 시 실패, 제외 허용치 0                                                |
| C4의 제목·시점 문서 경로·날짜·type·asOf·첫 기준일                                | 위반 시 실패                                                               |
| 동일 커밋의 문서 추가·삭제에 따른 ID 소실 검사                                   | 기존 예외·rename 판정을 보존하며 위반 시 실패                              |
| 동명 문서 충돌                                                                   | 실패                                                                       |
| 없는 링크 대상·없는 앵커                                                         | 기존 기본 심각도인 경고를 유지. 오류로 강화하는 별도 정책 변경을 섞지 않음 |
| 미해석 feed 참조                                                                 | 경로·커밋 SHA를 포함해 실패                                                |
| 억제 목록 파싱·스키마 오류                                                       | 실패                                                                       |
| 대응 feed가 없는 오래된 억제 항목                                                | 기존 경고 유지                                                             |
| summary·feeds·body 스키마와 참조·본문·트리·태그·세대·ID 유일성 불변식            | 위반 시 실패. feed 빌드 윈도우로 잘리기 전 전체 집합도 검사                |
| 검사에 필요한 Git 가용성·전체 이력                                               | 전제가 충족되지 않으면 원인을 포함해 실패                                  |

위 표는 현재 합의한 검사 이전의 목표 동작이다. 기존 규칙의 조건·예외·심각도·진단을 빠뜨리지 않는다. 옛 CLI의 help·argv·stdout 문자열·폐기된 명령 자체를 유지하기 위한 테스트는 제거할 수 있지만, 그 안의 실질 검사와 실패 원인 검증은 보존한다.

## C6. 기능 처리와 검사의 경계

summary·feeds·wiki·build는 호출된 기능의 입력 처리·파싱·변환·렌더·생성을 수행한다. 문서 전체의 작성 규칙, 중복·ID 변경·삭제 ID 재사용 감사, commit 규약·deadlink·산출물 간 전체 불변식 집행은 테스트가 소유한다. validate CLI나 같은 검사를 다른 이름으로 옮긴 전량 검사기를 기능 경로에서 호출하지 않는다.

인자 형식·허용 파일 경로·읽는 캐시의 스키마/환경/세대 확인·필수 파일 읽기 실패 등 해당 동작의 성립에 필요한 처리는 기능에 남는다. draft 가시성·disable·삭제 피드 정리·명시적 억제·파일명 제목·본문 렌더와 그에 필요한 Git 조회도 기능 처리다. 이력에서 값이나 피드를 구하는 작업과 전체 문서 ID의 불변성을 감사하는 작업을 구분한다.

전체 작성 규칙 집행은 dev/prod 검사 시 수행하고, 환경별로 파싱·Git 조회 결과를 공유한다. 기능 실행과 테스트가 필요로 하는 파서·렌더·변환을 복제하지 않는다. 동일 Git 질의의 중복과 정지한 자식 프로세스의 무한 대기를 피하는 방법은 구현 계획에서 정한다. 고정 시간 숫자나 공유 함수 이름은 이 계약에서 정하지 않는다.

검증을 통과한 입력에 대한 기존 API 필드·환경별 문서 집합·생성 데이터의 의미를 보존한다. 작성 규칙 위반 문서의 판정·진단은 문서 집행 테스트에서 확인한다.

## C7. 실패·진단·커버리지

- 실제 문서 위반의 실패에는 문서 경로·원인이 있어야 하고, feed 이력 관련 실패에는 해당 커밋을 식별할 수 있는 SHA가 있어야 한다.
- 검사 실패 전 확인 가능한 제외·prune·미해석 참조 진단을 유지한다. 기존 보고서를 테스트가 생성하는 경우 `logs/summary.report.<env>.json`과 `.txt`에 쓰며, 빌드의 필수 생성 단계로 두지 않는다.
- 실패와 보고서 쓰기 실패가 조용한 성공으로 바뀌지 않는다. 보고서에 필요한 사실을 얻기 전 파싱 자체가 실패한 경우에는 그 오류를 숨기지 않는다.
- 기존 제품 커버리지 floor인 statements 86·branches 76·functions 92·lines 89를 낮추지 않는다. 계측 대상은 scripts의 실제 기능 코드이며 테스트·도우미·하네스를 분모에 섞지 않는다.
- 회귀 검증은 정상 픽스처 통과와 위반 픽스처 실패, 검사 무력화·누락·실패 전달의 검출력을 확인한다. 테스트 개수 자체를 계약으로 고정하지 않는다.

## C8. Git 훅·CI·운영 산출물

```text
pre-commit → 기존 ID 자동 생성·검증
pre-push   → test → 실패하면 push 차단
CI         → 전체 이력 checkout → 설치 → 포맷 → test:coverage
           → build(prod) → 운영 산출물 저장
수동 개발  → test:harness
```

pre-commit의 기존 UUIDv7 발급·검증을 유지한다. 기존 ID를 새로 발급하지 않는다. CI에서는 커밋·push를 하지 않으며 필요한 전체 Git 이력과 명시적 설치를 준비한다.

build는 `cache/summary.prod.json`, `cache/feeds.prod.json`을 생성한다. build-dev는 대응하는 `.dev.json` 두 파일을 생성한다. 운영 빌드에 dev 산출물을 사용하지 않는다. 생성 중 실패하면 성공한 빌드로 취급하지 않는다.

CI는 테스트한 같은 커밋에서 두 prod 파일을 생성하고 같은 환경·sourceCommit의 한 세트로 저장한다. PR에서는 산출물 생성 가능성도 확인하고, 릴리즈가 사용할 세트는 main의 통과한 커밋 산출물로 식별한다. 재실행·서로 다른 커밋·환경의 파일을 섞어 사용하지 않는다. 실제 릴리즈 발행·다운로드·배포 연결은 이번 범위 밖이다.

## C9. 제거·확장·작업 제한

- 대체 검사가 동작한 뒤 `scripts/validate.mjs`, package의 validate 명령, 빌드·훅·CI·가이드·테스트의 옛 실행 참조를 제거한다. 새 이름의 독립 검증 CLI나 호환 껍데기를 남기지 않는다.
- 변경 범위는 `/workspace/sas-wiki` 내부다. 상위 `/workspace`의 규칙·소비처는 읽기 전용으로 참고하며 파일·설정·서브모듈 포인터·부모 커밋을 수정하지 않는다. 상위 소비자의 validate 존재 고정 등 호환성 영향은 기록·보고하고 별도 작업으로 남긴다.
- 향후 테스트 품질·TypeScript·커스텀 린트와 그 룰 검증은 별도 하네스 분야로 추가할 수 있다. 이번에는 린트 패키지·설정·커스텀 룰·빈 린트 폴더를 만들지 않는다.
- 보호된 harness 경로의 읽기·쓰기 차단을 우회하지 않는다. 실제 적용이 필요한 변경안을 검토 가능하게 준비한 뒤 해당 정책에 맞는 사용자 적용을 안내한다. 명세·계획 검수 전 적용을 요청하지 않는다.
- 작업은 현재 feature 브랜치에서 이어가며 커밋은 로컬에만 한다. 원격 push·PR 생성·배포·릴리즈 발행·훅 우회를 하지 않는다.

## C10. 계약의 확인과 변경

PRD·이 계약의 완전성 검수 뒤, 해당 페이즈 계획이 계약 항목·변경 대상·검증 방법을 빠짐없이 연결하는지 검수한다. 테스트 통과는 이 완전성 검수를 대신하지 않는다. 단계 상태는 PRD의 Implementation Phases 한 곳에서 관리한다.

폴더·파일의 구체 배치와 구현 방법은 실제 작업에서 조정될 수 있다. 합의한 책임·범위·외부 동작·명명 원칙이 달라지면 이유·영향·대안을 제시해 사용자와 조율한 뒤 PRD·이 문서·관련 계획을 맞춘다. 목표 동작을 충족하는 내부 방법의 조정은 해당 plan.md에 반영한다. 목표를 구현 상태에 자동으로 맞추거나 구현을 이유로 합의 변경을 확정하지 않는다.

작업 조사표·검수용 대조표·실험 결과를 별도 상시 명세로 늘리지 않는다. 구체적인 소스 소비처와 이전 순서는 해당 plan.md에, 검수 결과는 작업 보고·커밋 근거에 남긴다.
